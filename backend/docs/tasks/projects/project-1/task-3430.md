#### 1.2 requirement_tasks关联表

创建新表支持需求-任务多对多关联:

```sql
CREATE TABLE IF NOT EXISTS requirement_tasks (
    id SERIAL PRIMARY KEY,
    requirement_id INTEGER NOT NULL REFERENCES requirements(id) ON DELETE CASCADE,
    task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    link_type VARCHAR(20) NOT NULL DEFAULT 'manual',
    linked_by INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    link_comment TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    -- 唯一约束 - 防止重复关联
    CONSTRAINT unique_requirement_task_link UNIQUE (requirement_id, task_id),
    
    -- 关联类型: manual手动关联, converted需求转任务, related相关联
    CONSTRAINT check_link_type CHECK (link_type IN ('manual', 'converted', 'related'))
);
```

**6个优化索引**:
- 双向查询索引(通过需求查任务、通过任务查需求)
- 关联类型过滤索引
- 关联人查询索引
- 复合索引(需求+类型、任务+类型)

#### 1.3 自动化触发器

```sql
-- 触发器1: 自动同步mentioned_count字段
-- 在插入/更新评论时自动计算mentioned_user_ids数组长度
CREATE TRIGGER trigger_sync_mentioned_count
    BEFORE INSERT OR UPDATE ON requirement_comments
    FOR EACH ROW
    WHEN (NEW.mentioned_user_ids IS DISTINCT FROM OLD.mentioned_user_ids OR TG_OP = 'INSERT')
    EXECUTE FUNCTION sync_requirement_comment_mentioned_count();

-- 触发器2: 自动更新requirement_tasks的updated_at
CREATE TRIGGER trigger_requirement_tasks_updated_at
    BEFORE UPDATE ON requirement_tasks
    FOR EACH ROW
    EXECUTE FUNCTION update_requirement_tasks_updated_at();
```

#### 1.4 数据迁移

自动将现有数据迁移到新表结构:

```sql
-- 迁移已转换的需求(converted_task_id)到requirement_tasks表
INSERT INTO requirement_tasks (requirement_id, task_id, link_type, linked_by, link_comment, created_at)
SELECT
    r.id, r.converted_task_id, 'converted',
    COALESCE(r.converted_by, r.submitter_id),
    '从需求转换而来',
    COALESCE(r.converted_at, r.created_at)
FROM requirements r
WHERE r.converted_task_id IS NOT NULL
ON CONFLICT (requirement_id, task_id) DO NOTHING;
```

## 🔍 技术细节

### @用户提及实现原理

1. **前端输入**: 用户在评论中输入`@john @admin`,MentionInput组件实时解析
2. **API请求**: 前端发送`mentioned_user_ids: [1, 5]`到后端
3. **数据库存储**: 后端将数组存为JSONB: `[1, 5]`
4. **触发器同步**: `mentioned_count`自动更新为`2`
5. **查询优化**: 
   - 通过`mentioned_count > 0`快速过滤有提及的评论
   - 通过`mentioned_user_ids @> '[1]'::jsonb`查询提及了用户1的评论

### 需求-任务关联设计

**三种关联类型**:

1. **converted** (需求转任务)
   - 从需求详情页点击"转为任务"按钮
   - 自动填充任务表单(标题、描述、项目等)
   - 创建任务后建立converted类型关联
   - 原需求状态变为"converted"

2. **manual** (手动关联)
   - 在需求详情页的"关联任务"Tab点击"关联已有任务"
   - 搜索选择任务ID或标题
   - 建立manual类型关联,可添加关联说明

3. **related** (相关联)
   - 系统自动识别或用户标记的相关关系
   - 未来可扩展智能推荐功能

**查询场景**:
```go
// 查询需求REQ-001关联的所有任务
SELECT rt.*, t.title, t.status
FROM requirement_tasks rt
JOIN tasks t ON rt.task_id = t.id
WHERE rt.requirement_id = 123
ORDER BY rt.created_at DESC;

// 查询任务TASK-456关联的所有需求
SELECT rt.*, r.display_id, r.title, r.status
FROM requirement_tasks rt
JOIN requirements r ON rt.requirement_id = r.id
WHERE rt.task_id = 456
ORDER BY rt.created_at DESC;
```

## 📊 性能优化

### 索引策略

| 索引名称 | 索引类型 | 用途 | 预期性能提升 |
|---------|---------|------|-------------|
| `idx_req_comments_mentioned_users` | GIN | @用户反查评论 | 10-100x |
| `idx_req_comments_mentioned_count` | B-tree (条件) | 有提及评论过滤 | 5-10x |
| `idx_requirement_tasks_requirement` | B-tree | 需求→任务查询 | 10x |
| `idx_requirement_tasks_task` | B-tree | 任务→需求查询 | 10x |
| `idx_requirement_tasks_req_type` | 复合索引 | 需求+类型过滤 | 5x |
| `idx_requirement_tasks_task_type` | 复合索引 | 任务+类型过滤 | 5x |

### 数据量预估

假设系统规模:
- 1000个需求 × 平均5条评论 = 5000条评论
- 30%的评论有@提及(平均2个用户) = 1500条
- 70%的需求转为任务 = 700个关联
- 30%的需求关联已有任务(平均1.5个) = 450个关联

**存储空间**:
- `mentioned_user_ids`: 1500条 × 平均50字节 = 75KB
- `requirement_tasks`: 1150条 × 200字节 = 230KB

**查询性能**:
- 查询某用户被@的评论: <10ms (GIN索引)
- 查询需求关联的任务: <5ms (B-tree索引)

## 🔐 安全考虑

### SQL注入防护

所有查询使用参数化:
```go
// ✅ 正确 - 使用占位符
db.Where("mentioned_user_ids @> ?::jsonb", pq.Array([]int{userID}))

// ❌ 错误 - 字符串拼接
db.Where(fmt.Sprintf("mentioned_user_ids @> '[%d]'::jsonb", userID))
```

### 权限控制

**@用户限制**:
- 只能@同一企业的用户
- 内部评论只能@系统用户
- 每条评论最多@10个用户(前端验证+后端限制)

**关联任务限制**:
- 只能关联同一企业的任务
- 只有需求提交人、评审人、系统管理员可以创建关联
- converted类型关联不可删除(只能通过取消转换)
