# Warehouse模块目录结构创建方案

## 任务概述
创建Warehouse（仓库）模块的目录结构，为后续迁移Warehouse相关代码做准备。

## 背景分析

### 现有代码位置（主仓库）
位于 `coolbuy3.0-backend/internal/pms/` 目录下：
- **Model层**: warehouse_model.go, warehouse_express_model.go
- **Store层**: warehouse_store.go, warehouse_express_store.go
- **Biz层**: warehouse_biz.go, warehouse_express_biz.go
- **API层**: warehouse_api.go, warehouse_express_api.go
- **Ctrl层**: warehouse_controller.go, warehouse_express_controller.go

### 新架构设计（business-service）
新项目采用简化的两层架构：
```
paas-system/business-service/internal/
├── core/              # 核心功能
├── order/             # 订单模块
│   ├── model/         # 数据模型
│   └── handler/       # 处理器（业务逻辑+API）
├── product/           # 产品模块
│   ├── model/
│   └── handler/
├── warehouse/         # 仓库模块（待创建）
│   ├── model/         # 数据模型
│   └── handler/       # 处理器
└── router/            # 路由配置
```

### 架构对比
| 老架构 (PMS) | 新架构 (Business Service) |
|-------------|--------------------------|
| model + store + biz + api + ctrl (5层) | model + handler (2层) |
| 职责分散 | 职责整合 |

## 技术说明

### 新架构优势
1. **简化层次**: 减少5层到2层，降低复杂度
2. **职责清晰**: handler整合业务逻辑和API处理
3. **易于维护**: 减少文件跳转，提高开发效率
4. **统一规范**: 与order/product模块保持一致

### 迁移策略
- **Model层**: 基本保持不变，调整import路径
- **Handler层**: 整合store/biz/api/ctrl的功能
  - 数据访问逻辑（store）→ handler内部实现
  - 业务逻辑（biz）→ handler方法
  - API接口（api+ctrl）→ handler的HTTP处理函数
