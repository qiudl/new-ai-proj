## 架构对比

### 老架构（4层）
```
Request → Controller → Biz → Store → DB
                ↓       ↓      ↓
              API    Model  Query
```

**特点**：
- Controller: 绑定参数，调用Biz
- Biz: 数据转换（copier），调用Store
- Store: 构建查询，执行DB操作
- API: 定义请求响应结构

### 新架构（单层Handler）
```
Request → Handler → DB
            ↓
        Model + DTO
```

**特点**：
- Handler直接处理所有逻辑
- 从context获取租户DB
- 内部定义请求响应结构
- 直接使用GORM操作数据库

## 关键适配点

### 1. 租户数据库获取
```go
// 老架构
s.TenantDB(c)  // 从Store获取

// 新架构
db, err := middleware.GetTenantDB(c)  // 从中间件获取
```

### 2. 参数绑定
```go
// 老架构
core.BindQuery[api.ReqListWarehouse](c)
core.Bind[api.ReqCreateWarehouse](c)

// 新架构
c.Query("code")  // 查询参数
c.ShouldBindJSON(&req)  // JSON参数
strconv.ParseUint(c.Param("id"), 10, 32)  // 路径参数
```

### 3. 响应格式
```go
// 老架构
core.Write(c, resp, err)  // 统一封装

// 新架构
c.JSON(http.StatusOK, gin.H{"data": data})  // 标准gin响应
c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
```

### 4. 错误处理
```go
// 老架构
返回error，由core.Write统一处理

// 新架构
if err != nil {
    if err == gorm.ErrRecordNotFound {
        c.JSON(http.StatusNotFound, gin.H{"error": "Not found"})
    } else {
        c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
    }
    return
}
```

### 5. 分页查询
```go
// 老架构
core.Paginate[*model.Warehouse](query, r)  // 统一分页

// 新架构
// 需要手动实现分页逻辑
page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
limit, _ := strconv.Atoi(c.DefaultQuery("limit", "20"))
offset := (page - 1) * limit
query.Offset(offset).Limit(limit)
```

### 6. 复杂查询（WarehouseExpress）
```go
// 老架构的JOIN查询
query.Select(
    "we.*",
    "pms_express.name as _express_name",
    "pms_express.code as _express_code",
)
query.Joins("inner join pms_warehouse_express we on we.express_id = pms_express.id")

// 新架构需要适配

```

## 技术说明

### 简化带来的优势
1. **代码集中**: 一个handler文件包含所有逻辑，易于理解
2. **减少转换**: 不再需要copier在多层之间转换数据
3. **直接操作**: Handler直接操作DB，减少中间层开销
4. **灵活性高**: 可以更灵活地处理特殊业务逻辑

### 需要注意的问题
1. **复杂查询**: 手动构建GORM查询（如JOIN）
2. **代码复用**: 公共逻辑需要抽取为辅助函数
3. **测试编写**: Handler包含更多逻辑，测试需要更全面
