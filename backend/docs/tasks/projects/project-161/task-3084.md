# Category Handler更新方案

## 任务概述
更新现有的Category Handler，从直接操作数据库改为调用新的Ctrl层，完成分层架构的集成。

## 现状分析

### 现有Handler架构
当前`handler/category.go`（203行）采用简化架构：
- **直接数据库操作**: Handler层直接调用`db.Create/Find/Save/Delete`
- **无业务逻辑**: 缺少HasChildren检查、父分类验证等
- **简单响应**: 直接返回模型数据

### 新Ctrl层架构
已完成的`ctrl/category.go`（212行）采用标准分层：
- **调用Biz层**: Ctrl → Biz → Store → DB
- **完整业务逻辑**: 包含验证、检查、转换
- **结构化响应**: 使用API定义的DTO

### 路由注册


## 架构决策

### 方案选择
**选择方案B**: 更新Handler调用Ctrl层（推荐）

**理由**:
1. ✅ Handler作为适配层，保持路由层清晰
2. ✅ Ctrl层已经实现完整业务逻辑
3. ✅ 符合分层架构最佳实践
4. ✅ 无需修改路由注册代码

**替代方案A**（不采用）: 直接在路由中使用Ctrl
- ❌ 混淆Handler和Ctrl的职责边界
- ❌ 需要修改路由注册代码

## 实施方案

### 1. Handler职责定位
Handler作为**适配层**，职责：
- 获取租户DB连接（调用middleware.GetTenantDB）
- 参数验证和绑定（使用Gin的绑定功能）
- 调用Ctrl层方法
- 处理错误并返回HTTP响应

### 2. 代码结构

```go
type CategoryHandler struct {
    ctrl *ctrl.CategoryCtrl
}

func NewCategoryHandler(db *gorm.DB) *CategoryHandler {
    return &CategoryHandler{
        ctrl: ctrl.NewCategoryCtrl(),
    }
}

func (h *CategoryHandler) List(c *gin.Context) {
    db, err := middleware.GetTenantDB(c)
    if err != nil {
        c.JSON(500, gin.H{"error": "Tenant context not found"})
        return
    }
    
    var req api.ReqListCategory
    if err := c.ShouldBindQuery(&req); err != nil {
        c.JSON(400, gin.H{"error": err.Error()})
        return
    }
    
    // 调用Ctrl层（Ctrl层内部会调用Biz和Store）
    h.ctrl.List(c)
}
```

### 3. 与Ctrl层的关系

**Handler层**:
- 处理HTTP协议细节
- 参数绑定和验证
- 错误转换为HTTP状态码
- 响应格式化

**Ctrl层**:
- 已实现完整的参数绑定
- 已实现完整的错误处理
- 已实现完整的响应格式化

**简化方案**: Handler直接调用Ctrl的方法
- Handler只需获取DB，其他全部交给Ctrl

## 优势分析

### 1. 职责分离
- **Handler**: HTTP适配层（简化为5-10行/方法）
- **Ctrl**: 控制器层（完整的HTTP请求处理）
- **Biz**: 业务逻辑层
- **Store**: 数据访问层

### 2. 代码复用
- Ctrl层可以被其他入口复用（如gRPC）
- Handler层专注于Gin框架适配

### 3. 易于测试
- Ctrl层包含完整逻辑，便于单元测试
- Handler层极简，减少测试复杂度

### 4. 易于维护
- 逻辑集中在Ctrl/Biz层
- Handler层变更少，稳定性高
